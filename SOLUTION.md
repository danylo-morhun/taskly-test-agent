# Solution: unit-test agent and agentic PR workflow

A Claude Code **custom agent** (`unit-test-agent`) with **five reusable skills**. On every pull request it decides where unit tests are needed, writes or updates them for the backend and frontend, proves them (tests, typecheck, flakiness, patch coverage, mutation testing), and publishes the result to the PR as a sticky report plus a separate PR with the tests. It never touches production code.

## How it works

```
pull_request ─► context ─► detect ─► generate ──► verify ──► publish
                (API)     (no LLM)  (LLM agent)  (no LLM,   (App token,
                                     read-only    no         never runs
                                     token        secrets)   PR code)
```

1. **context**: resolves the PR (also via `workflow_dispatch`). Skips forks, drafts, the `test-agent:skip` label, the agent's own PRs, and PRs whose base branch does not have the agent yet.
2. **detect** (deterministic): `detect-changes.mjs` classifies every changed file as `source`, `test`, `excluded` (the project's own coverage exclusions) or `other`, using `config.json`. With no testable source change the LLM is never called: no cost, no nondeterminism. On `synchronize`, a push that changed none of the PR's source files since the last *fully analyzed* head is skipped too: for example, merging the agent's test PR or a rebase. That head is recorded in the report comment only after a complete run, so a cancelled or failed run never counts.
3. **generate**: `claude-code-action` runs `claude --agent unit-test-agent --settings .claude/test-agent/agent-settings.json`. The agent follows its skills: plan per file, write tests in house style, run → triage → fix, full suite, patch coverage, mutation testing on the changed lines, final `verify.mjs`, then a schema-validated `report.json`. If a previous proposal exists for the PR, it is applied first, so later pushes **update** tests instead of regenerating them.
4. **verify** (independent, no secrets): fresh checkout of the PR head plus a *trusted* checkout of the base branch's tooling. It measures baseline coverage, applies the agent's patch and re-runs everything: path policy, typecheck, Prettier, full suites with coverage, 3× shuffled re-runs of changed tests, patch coverage before → after, and mutation score. It also validates the agent's report against its JSON Schema and checks one decision per changed file.
5. **publish** (GitHub App token, no PR code executed): if verification passed, it pushes the tests to `test-agent/pr-<n>` (based on the PR head) and opens or updates a PR **into the feature branch**. It then upserts one sticky report comment on the original PR and the job summary. The check fails when the generated tests do not verify.
6. **cleanup**: closing the PR closes the test PR and deletes its branch.

### The agent and its skills

The agent prompt (`unit-test-agent.md`) defines the role, inputs, the order of skills, hard rules and the output contract. The procedural knowledge lives in skills, loaded on demand through the Skill tool (progressive disclosure: a frontend-only PR never loads the backend skill):

| Skill | Responsibility | Deterministic scripts |
| --- | --- | --- |
| `test-impact-analysis` | Per-file decision table: add / update / no tests needed / skip. Where tests belong. Risk-first prioritization | `detect-changes.mjs` |
| `backend-unit-tests` | Express/Prisma/Zod conventions and seams (fake repository + supertest, spied Prisma delegates, `vi.stubEnv`, mocked process lifecycle) + `references/patterns.md` | — |
| `frontend-unit-tests` | React/RTL/TanStack Query conventions (design-system mocks, fresh `QueryClient`, stubbed `fetch`, fake timers, Prettier) + `references/patterns.md` | — |
| `test-verification` | The run → triage → harden loop: **test bug vs. source bug vs. stale setup vs. regression**, patch coverage, mutation survivors, flakiness | `run-tests.mjs`, `patch-coverage.mjs`, `mutation-test.mjs`, `check-test-policy.mjs`, `verify.mjs` |
| `test-report` | Report contract and rendering | `validate-report.mjs`, `render-report.mjs`, `summarize-run.mjs`, `report.schema.json` |

The skills use only the portable frontmatter fields (`name`, `description`, `license`, `compatibility`, `metadata`), so they also load outside Claude Code. They are driven by `config.json`: another repository reuses them by declaring its workspaces (sources, tests, exclusions, protected files).

The same agent runs locally: `claude --agent unit-test-agent --settings .claude/test-agent/agent-settings.json "PR mode. Base: origin/main."`. The baseline coverage in #3/#4 was produced that way, with two agents running in parallel in separate git worktrees.

## Main technical decisions

| Decision | Why |
| --- | --- |
| **Claude Code + `claude-code-action`** | Native custom agents, skills, hooks and permission system, with a maintained GitHub Action that restores `.claude/` from the base branch on PRs (a PR cannot rewrite its own reviewer). Supports OAuth (subscription) or API-key auth. |
| **LLM only where judgment is needed** | Change detection, test execution, coverage, mutation testing, policy and rendering are plain Node scripts with unit tests. The agent calls the same scripts CI uses, so "it passed for me" and "it passed in CI" mean the same thing. |
| **Separate verify job that does not trust the agent** | The agent's self-report is shown *next to* independently measured results. A false claim is visible, and failing tests are never proposed. |
| **Mutation testing (StrykerJS) on changed lines** | Coverage shows tests ran the code. Mutation score shows they would catch a change. Survivors, with the exact source fragment, are fed back to the agent to sharpen assertions. |
| **Patch coverage (before → after)** | Whole-repo coverage hides whether *this* change is tested. Like Codecov, only the PR's changed executable lines count. |
| **Tests proposed as a stacked PR, not pushed to the author's branch** | Same model as Dependabot/Renovate: the human stays in control. A bad generation can be closed, not reverted. The force-updated branch keeps one proposal per PR. |
| **GitHub App for publishing** | `GITHUB_TOKEN` pushes do not trigger workflows, so CI would never run on the test PR. The App gives short-lived scoped tokens and a distinct bot identity. Falls back to `GITHUB_TOKEN` if not configured. |
| **Structured, schema-validated report** written to a file | `--json-schema` structured output is not honored with `--agent` (the agent prompt replaces the system prompt). A file plus a dependency-free validator plus a self-correction loop works the same locally and in CI. |
| **Stale setup ≠ regression** | A new interface member breaking an old mock is a setup fix. A changed assertion outcome is a regression, reported and left untouched unless the PR states the change is intended. This keeps the agent from "fixing" tests to match bugs. |

## Security model

The agent processes untrusted input (PR diff, title, description) and runs untrusted code (tests). Each layer assumes the one before it failed.

| Threat | Control |
| --- | --- |
| Fork PR / outside contributor | Fork PRs skipped. Repo setting requires approval for outside contributors. `claude-code-action` additionally checks the actor has write access |
| PR modifies the agent, skills, hooks or settings | `claude-code-action` restores `.claude/` from the base branch. Verify and publish run tooling from a separate **base** checkout (`TEST_AGENT_REPO_ROOT` points scripts at the PR checkout) |
| Prompt injection in PR text or code | Prompt marks PR context as untrusted data. The agent has no network tools (WebFetch/WebSearch/Agent denied), cannot run arbitrary shell, and cannot write outside test paths. Its output is re-verified and its text is sanitized before rendering (HTML, links, images, `@mentions`, `#refs`, table syntax neutralized) |
| Token exfiltration via tests (PR code runs) | The only job holding the LLM credential has a **read-only** `GITHUB_TOKEN`. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` + **bubblewrap** give agent subprocesses a scrubbed env and their own PID namespace. `npm ci --ignore-scripts`. The one pre-agent step that evaluates PR code (`prisma generate` → `prisma.config.ts`) runs in a bubblewrap PID namespace with `--die-with-parent`, so nothing outlives it. Test scripts spawn Vitest/Stryker with an **allowlisted environment** |
| Agent tampers with its own inputs | `detect.json` / `pr-context.md` are read-only to the agent (both hooks). Verify and publish read change detection from the trusted `detect` artifact, never from agent output |
| Agent edits production code / weakens tests | `guard-test-paths.mjs` hook (symlink-safe) allows only test files and helpers (`setup.ts` protected). Verify re-checks the patch: no source changes, no deleted tests, no `.only/.skip`, no assertion-free files. It warns on removed test cases or fewer assertions. Publish re-checks again before committing |
| Agent runs arbitrary commands | `permissions.defaultMode: dontAsk` + allowlist, plus `guard-bash.mjs`: only skill scripts and read-only git, no chaining/pipes/redirection/substitution, script outputs confined to `.test-agent/` |
| Write tokens near untrusted code | `contents: write` / App token only in `publish`, which checks out the base branch and only applies a verified patch (`git apply`, no hooks, no installs). Push via `GIT_CONFIG_*` header, not the URL |
| Supply chain | All actions pinned to commit SHAs (releases ≥ 2 weeks old). `persist-credentials: false`. `permissions: {}` at the top, granted per job. zizmor + actionlint in CI. Dependabot for npm and actions |
| Runaway cost / loops | Deterministic skip before the LLM, per-PR `concurrency` with cancel, `timeout-minutes`, `--max-turns`, file budget (`maxSourceFiles`), the agent's own PRs ignored, test-only pushes skipped |

## Running it

**Prerequisites**
- Repository secret `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`, uses a Pro/Max subscription) **or** `ANTHROPIC_API_KEY`.
- Recommended: a GitHub App with *Contents: read & write* and *Pull requests: read & write*, installed on the repo. Set variable `TEST_AGENT_APP_CLIENT_ID` and secret `TEST_AGENT_APP_PRIVATE_KEY`.
- Optional: variable `TEST_AGENT_MODEL` (default `claude-opus-5-5`).
- The agent must be on the default branch: PRs are analyzed with the base branch's agent.

**Triggers**
- Automatic: opening, updating, reopening a PR or marking it ready.
- Manual: *Actions → Test Agent → Run workflow* with a PR number (`gh workflow run test-agent.yml -f pr=<n>`).
- Opt out per PR: label `test-agent:skip`.

**Locally**
```bash
(cd backend && npm ci) && (cd frontend && npm ci)
claude --agent unit-test-agent --settings .claude/test-agent/agent-settings.json "PR mode. Base: origin/main."
node .claude/skills/test-verification/scripts/verify.mjs --base origin/main --mutation   # same checks as CI
node --test '.claude/test-agent/test/*.test.mjs'                                          # tooling tests
```

## Example runs

All runs are public on the [Actions tab](../../actions/workflows/test-agent.yml). Each report is the sticky comment on the PR (GitHub keeps its edit history).

### 1. Feature PR [#5](../../pull/5): "Clear completed" (backend + frontend, no tests)

**Push 1** contained a realistic bug: `DELETE /completed` was registered after `DELETE /:id`, so the id validator answered 422.

- **detect**: 7 testable files (repository, router, api, hook, button, page, utils), 2 coverage-excluded (`types.ts`, `queryKeys.ts`), 1 other (`openapi.json`).
- **Skills invoked** (from the transcript, not self-reported): `test-impact-analysis` → `backend-unit-tests` → `frontend-unit-tests` → `test-verification` → `test-report`.
- **Decisions**: `added_tests` for `ClearCompletedButton` and `useClearCompletedMutation`, `updated_tests` for the other five. `router.test.ts` and `TodosPage.test.tsx` were classified as **stale setup**: a mock was missing the new method or hook. The setup was updated and every existing assertion kept.
- **Concern** (production code untouched): *"`router.ts:35`: DELETE /completed is registered after DELETE /:id … returns 422 instead of 200 … Fix: register the /completed route before /:id."*
- **Verification**: backend 111/111 and frontend 174/174, typecheck ✅, 3× shuffled ✅, frontend patch coverage 100% and mutation 97.5%. The backend threshold warning (⚠️) came from the unreachable route. Tests were proposed as PR [#11](../../pull/11) by `taskly-test-agent-bot`, and CI ran on it (GitHub App token).
- About 60 turns and 6–8 minutes per run.

**Push 2** fixed the route order, following the concern. The agent reused the previous proposal, kept its tests and added `DELETE /api/todos/completed` cases (200 with count, zero count, and `repository.delete` *not* called, which guards against the bug coming back). Backend patch coverage went **25% → 100%** and mutation **100% (7/7)**. The same PR #11 was updated rather than duplicated.

**Merging #11** into the feature branch triggered a run that was skipped deterministically ("no testable source file of this PR changed since the last analyzed commit"). No LLM call.

### 2. Regression PR [#12](../../pull/12): "refactor: extract validation length limits into constants"

The "refactor" silently lowered the title limit from 120 to 100. The agent changed **no tests**:
- **Regression**: `validators.test.ts > accepts every input field and boundary lengths`. The test was left untouched, because the PR describes a behavior-preserving refactor.
- **Concerns**: the hidden API behavior change, plus a **frontend/backend mismatch** the agent found on its own: `validateTodo` still allows 120 characters, so titles of 101–120 characters pass the client and fail on the server.
- The check is red, as is backend CI.

### 3. Tooling, config or docs-only PRs (e.g. [#2](../../pull/2), [#6](../../pull/6), this PR)

**detect** found no testable source, so the run was skipped in about 20 s with no LLM call, and a short "Skipped" report was posted.

### 4. Baseline coverage ([#3](../../pull/3), [#4](../../pull/4))

These used the same agent in *target mode*, run locally: two agents in parallel, in separate git worktrees. Backend took 47 turns and 3.3 minutes; frontend took 126 turns and 11 minutes. See the coverage table at the top.

### Problems found by dogfooding and code review, and fixed (PRs #2, #6–#10, #13, #15)

The live runs surfaced real integration issues, each fixed in its own PR:
- `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` needs bubblewrap. It is now installed, so isolation is not disabled.
- Agent frontmatter hooks are ignored without workspace trust in headless mode. They are now enforced through `--settings`.
- The sandbox creates empty placeholder files: an empty root `package.json` broke Vite's root lookup, and placeholders showed up in the self-check.
- Exclude pathspecs fail on ignored paths. Run output had leaked into the patch, and the independent policy check caught it.
- Coverage thresholds failing because of the PR's own unreachable code blocked valid tests. Thresholds are now a warning in verification and still a required check in CI.
- Rebases were not handled correctly by incremental skips. A skip also overwrote the last report.
- Mutation feedback did not show the original source fragment.
- A `/code-review` pass over `.claude/` and `.github/` found 10 issues, all fixed in #15. Examples: verify trusting an agent-writable `detect.json`, PR code running before the agent outside the sandbox, publishing a test PR despite an invalid report, unhandled Vitest errors counted as a pass, Dependabot PRs failing publish, and consistent failures reported as flaky.

## Assumptions

- Contributors with write access are trusted to run code in CI (the usual GitHub model). The agent targets same-repo PRs.
- "Unit tests" means hermetic tests at the module boundary: no PostgreSQL, network or browser. Integration/E2E tests are out of scope.
- The project's existing coverage exclusions (design system, types, barrels, entry points) reflect intent and are respected.
- A Claude Pro/Max OAuth token is acceptable for a demo. Production would use an organization API key or workload identity federation.
- Proposing tests in a separate PR is preferable to pushing into the author's branch.

## Limitations

- **Cost/latency**: one run takes about 5–15 minutes and a few dollars of tokens. Mutation testing is the slowest verification step. Large PRs are capped by `maxSourceFiles`.
- **Nondeterminism**: two runs can produce different (valid) tests. Verification bounds quality but not style.
- **Equivalent mutants** are judged by the agent, not proven. The score is a signal, not a gate.
- **Harden-runner runs in audit mode**: egress is logged, not blocked. Block mode needs an observed endpoint allowlist.
- **Same-runner isolation**: PR code (npm, tests) and the agent share a VM within the generate job. bubblewrap and env scrubbing reduce, but do not eliminate, the risk for a malicious *trusted* contributor.
- The agent judges "intended behavior change" from the PR text. A misleading description could make it update a test that should have been reported as a regression (the change is still visible in the test PR's diff).
- `--json-schema` structured output cannot be combined with `--agent` today, hence the file-based report.

## What I would change for production

- **Isolation**: run the agent in an ephemeral container or microVM with an egress allowlist (Anthropic API + npm mirror only), harden-runner in `block` mode, and dependency install in a separate job feeding a read-only cache.
- **Auth**: workload identity federation (`anthropic_federation_rule_id`) instead of a static token, with per-repo spend limits and alerting.
- **Quality gates**: make patch coverage and mutation score on changed lines required checks with thresholds. Track flaky-test history.
- **Evals**: a regression suite of fixture PRs (expected decisions: test / skip / regression / concern) run on every change to the prompt or skills, with pass-rate and cost trends.
- **Scale**: split large PRs per workspace into parallel subagents, cache Stryker incremental results, and use a smaller model for analysis and a stronger one for writing.
- **Feedback loop**: learn from accepted, edited and closed test PRs (review comments into skill references). Support `/test-agent` comment commands for collaborators.
- **Packaging**: ship the agent and skills as a Claude Code plugin with config-only adoption in other repositories.
